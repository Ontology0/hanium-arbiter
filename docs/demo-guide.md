# 컬처핏(Culture-Fit) 시연 안내

편집된 시연 영상·한국어 자막·대본·재생성 안내는 [영상 폴더](video/README.md)에 모은다. 아래는 현장에서 직접 동작을 설명할 때 사용하는 상세 시나리오다. 공식 제출본은 [2026 서식 Word](submission/TEAM_NUMBER_PENDING.docx)·[PDF](submission/TEAM_NUMBER_PENDING.pdf)를 사용한다.

시연 목적은 Slack의 장황한 에이전트 대화에서 합의·쟁점·다음 행동과 사람의 개입 지점을 확인하는 것입니다. 미확인 인계와 결정권자 부재는 이를 보여주는 사례이며, Pickle은 보조 예시입니다. 실제 Slack 워크스페이스 연결이나 외부 전송·모델 성능 비교를 완료한 것으로 설명하지 않습니다.

## 시작

프로젝트 루트에서 실행합니다.

```bash
uv sync
uv run uvicorn arbiter.app:app --app-dir backend --host 127.0.0.1 --port 8787
```

브라우저에서 [협업 관제 화면](http://127.0.0.1:8787/workspace)을 엽니다. [소개 페이지](http://127.0.0.1:8787/)에서는 관제로 이동할 수 있습니다. API 키 없이 진행하려면 실행 모드를 **통제 시뮬레이션**으로 유지합니다. 서버를 닫아도 SQLite에 저장된 세션은 남으므로 새 시연은 새 세션으로 시작합니다.

## 1. Slack 대화에서 핵심 결정 찾기 — 약 2분

“대화 가져오기”에서 아래 익명 예시를 입력합니다. 실제 사용자 이름과 비공개 대화는 사용하지 않습니다.

```text
개발 A: 배포 전 최종 승인 여부는 담당자에게 확인해볼게요.
검토 B: 검토 항목을 정리했습니다. 승인 답변을 받으면 다음 단계를 진행하겠습니다.
```

1. **현황:** 대화의 현재 쟁점과 필요한 확인을 읽습니다. Codex CLI가 준비됐다면 **브리핑 생성**으로 합의·쟁점·개입 지점·다음 행동을 확인하고 인용을 눌러 원문으로 이동합니다. 확인 약속이 관찰됐지만 전달·외부 작업 완료는 미확인이며 이 두 발화만으로 무한 대화라고 단정하지 않습니다.
2. **대화:** 원문과 발화자를 확인합니다. 목록은 페이지 단위로 탐색합니다.
3. **결정함:** 전달 상태 점검 요청에서 “요청 담당자 지정”을 선택하고 “개발 A가 배포 책임자에게 승인 여부를 확인하고 이 세션에 응답을 기록한다”를 메모로 입력합니다. 승인자 확인 요청도 실제 역할에 맞게 기록합니다.
4. **현황·결정함:** 다음 행동과 결정 이력이 저장됐는지 확인합니다. 실제 메시지가 전송됐다고 말하지 않습니다.
5. **지식맵:** 에이전트·확인 약속·결정 요청의 연결을 확인합니다.

이미 질문을 전달한 상황을 보여주려면 새 세션에서 같은 입력을 사용하고 “이미 요청함·응답 대기”를 선택합니다. 메모에는 전달한 사람·경로와 응답 대기 사유를 기록합니다. 이는 사람의 보고이며 시스템이 발송 영수증을 직접 확인한 것과 구분합니다.

## 2. 상호 검토 대기 — 약 1분

새 대화로 다음 예시를 가져옵니다.

```text
검토 A: 검토 B의 검토가 끝나면 제 검토를 진행하겠습니다.
검토 B: 검토 A의 검토가 끝나면 최종 내용을 확인하겠습니다.
```

결정함의 상호 대기 후보와 최종 결정권자 확인 요청을 봅니다. “담당자 직접 지정”을 선택하고 선행 검토자와 최종 승인자를 구분해 기록합니다. 원문에서 승인자를 찾지 못했다는 사실과 실제로 승인자가 없다는 판단은 다르다는 점을 설명합니다.

## 3. 중단·결정·재개 — 약 1분

새 통제 시뮬레이션에서 **피클의 주인 확인 약속 / 적응형 HITL**을 선택합니다. 실행을 시작하면 결정 대기에서 멈춥니다. 참석 여부를 선택한 뒤 실행을 재개하여 로컬 조율 계획의 체크리스트가 충족되는지 확인합니다.

이 단계의 에이전트 발화와 후속 산출물은 스크립트입니다. 완료는 계획 JSON의 조건 충족이며 실제 사람의 참석이나 외부 전송 완료를 뜻하지 않습니다. 원시 근거는 JSON 또는 Markdown으로 내려받을 수 있습니다.

## 4. 실험 결과 — 약 1분

실험 탭을 열어 24회 통제 시뮬레이션 결과를 확인합니다. 결과가 없으면 다음 명령을 실행한 뒤 새로 불러옵니다.

```bash
PYTHONPATH=backend python experiments/run_comparison.py --output experiments/results/latest
```

| 정책 | 성공 | 평균 턴 | 개입 요청 합계 |
|---|---:|---:|---:|
| 고정 턴 상한 | 2/8 | 14.75 | 0 |
| 주기적 HITL | 8/8 | 5.00 | 7 |
| 적응형 HITL | 8/8 | 5.00 | 6 |

설명 문구: “주기적 정책과 적응형 정책은 성공 수와 대화 턴이 같았습니다. 적응형은 정상 진행 사례의 요청 1건을 줄였습니다. 스크립트와 자동 응답에 의한 개입 기능 검증이며, 브리핑 품질·읽기 부담 감소·토큰 절감을 입증한 결과는 아닙니다.”

## 5. 에이전트가 직접 사용하는 MCP — 약 1분

[연결 설정 탭](http://127.0.0.1:8787/workspace#integration)과 [MCP 연결 안내](mcp-connection.md)를 확인합니다. 서버는 다음 명령으로 독립 실행할 수 있지만 stdio 모드는 MCP 클라이언트가 시작하도록 설정하는 방식이 일반적입니다.

```bash
uv run python -m arbiter.mcp_server
```

8개 도구는 대화 등록·발화 기록·상태·사람 결정·다음 행동·권한 조회와 권한 평가를 제공합니다. 사람의 결정·위임을 생성하거나 Slack에 메시지를 보내는 도구는 없습니다. 실제 프로토콜과 격리한 API를 사용한 연동 테스트는 수행했지만 실제 Pickle·Slack 계정은 연결하지 않았습니다. 보고할 사건마다 안정적인 `event_id`를 사용하고 동일 사건의 재시도에서는 같은 값을 유지합니다.

## 6. 다른 에이전트가 분석을 맡기는 A2A — 약 1분

```bash
uv run python -m arbiter.a2a_server
```

[AgentCard](http://127.0.0.1:8789/.well-known/agent-card.json)를 열어 분석 능력과 JSON-RPC 주소를 확인합니다. [A2A 연결 안내](a2a-connection.md)의 공식 SDK 예제로 대화를 전송하면 기존 분석 엔진이 브리핑을 만들고 task를 통해 반환합니다. 실제 분석에는 Codex CLI가 필요합니다. 모델 없이 연결 기능만 검증하려면 `uv run pytest tests/test_a2a.py -q`를 실행하며 이는 모의 브리핑 API를 사용하는 프로토콜 검증이라고 설명합니다.

HITL은 **어떤 상태에서 사람이 필요한지 탐지**, A2A는 **다른 에이전트의 분석 작업 위임**, MCP는 **에이전트가 작업 중 사건을 보고하고 사람 결정을 조회**하는 역할입니다. A2A task 완료는 분석 완료이고 Slack 전송이나 사람의 승인 완료가 아닙니다.

## 7. Slack 수신 — 토큰 설정 후에만 시연

[Slack 연결 안내](slack-connection.md)에 따라 읽기 전용 앱·토큰·채널 허용 목록을 준비하고 Socket Mode 수신기를 실행합니다. 설정 여부와 이벤트 수신 여부를 구분하여 새 메시지가 대시보드에 들어오는지 확인합니다. 현재 기록은 실제 워크스페이스에 연결한 결과가 아니므로 토큰 없이 연결 성공을 시연하지 않습니다.

## 마무리와 점검

- **연결 설정**은 외부 에이전트의 접속 방법을 안내하는 화면입니다. 설정 정보가 있다는 이유만으로 Pickle·Slack에 연결되었다고 설명하지 않습니다.
- 요청 카드의 처리와 외부 행동 완료를 구분하고, 미확인을 실패 또는 성공으로 바꾸어 설명하지 않습니다.
- 원시 결과는 [실험 보고서](../experiments/results/latest/report.md), 현재 구현·변경 배경은 [개발보고서](development-report.md), 공식 제출용 문서는 [서식 작성본](submission/TEAM_NUMBER_PENDING.docx)에 연결돼 있습니다.
- 서버나 실제 모델 호출이 오류를 반환하면 오류 메시지를 먼저 확인합니다. 시연에 실제 모델이 꼭 필요한 것은 아니며, 통제 시뮬레이션 결과와 실제 모델 기록은 별도로 설명합니다.
